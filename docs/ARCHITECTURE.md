# 設計資料

## 全体構成

- 画面は Next.js の Server Components で描画し、更新は Server Actions に集約する
- DB へのアクセスはすべてサーバー側。トランザクションごとに `role = authenticated` と JWT 情報（`request.jwt.claims`）を設定してから SQL を実行するため、RLS が必ず効く（`src/lib/db/rls.ts`）
- ブラウザは Supabase Realtime で配送案件・通知の変更を購読し、届いたら画面を再取得する。切断・再接続・画面復帰・通信の回復時も再取得するので、表示は常に DB の内容が正
- 秘密情報（`DATABASE_URL` など）はサーバー専用の環境変数。ブラウザに渡すのは Supabase の公開キーのみ

## データベース

会社（`companies`）をテナントとして、すべての表に `company_id` を持たせる。主キーは UUID、金額は `numeric(12,0)`（円）、日時は `timestamptz`、業務日付は日本時間。

主な表：`companies` `profiles` `offices` `drivers` `vehicles` `vehicle_assignments` `clients` `delivery_orders` `delivery_status_logs` `delivery_notes` `expenses` `notifications` `audit_logs`

### DB 側で守るルール（`20261027000002_business_rules.sql`）

- ステータス遷移：未割当 → 配車済 → 集荷完了 → 配送中 → 配送完了。例外は 配送失敗（集荷完了・配送中から）とキャンセル（集荷前まで）。配送失敗 → 配車済（再配達）、配車済 → 未割当（配車解除）。それ以外はトリガーで拒否
- ステータスが変わるたびに履歴を自動保存（変更者・メモ付き）。配送完了時に完了日時を記録
- ドライバーの付け外しでステータスを自動で揃える（付けたら配車済、外したら未割当）
- 保存禁止：休職中・退職済みのドライバー、整備中・廃車の車両への割り当て、完了済み案件の担当変更
- 予定の重複は「警告」（保存は可能）。画面側で確認ダイアログを出す

### マスタのルール（`20261027000009_master_rules.sql`）

- 管理コード（D-001 / V-001 / C-001）は未指定なら会社内の最大番号 + 1 を自動で振る（同時登録に備えてロック）
- 対応中（配車済・集荷完了・配送中）の案件があるドライバーは休職・退職にできない。対応中の案件で使っている車両は整備中・廃車にできない
- 退職・廃車にすると現在の担当車両の割り当てを今日で終える。退職者・廃車は新しく担当にできない
- 経費・担当車両に紐づけるドライバー・車両は同じ会社のものだけ
- 画面（選択肢を無効化）→ サーバー処理（理由付きのエラー）→ DB トリガー の3か所で同じルールを守る

### 荷主への請求（`20261027000010_client_invoices.sql`）

- 月末締め。締め済みの月（前月以前）の、配送完了・未請求の案件を荷主ごとにまとめて請求にする（`issue_client_invoice()`）。月の区切りは売上と同じ配送予定日
- 請求番号は会社ごと・対象月ごとの連番（`INV-202609-001`）。発行時の件数・金額を保存する
- 請求済みの案件は料金・荷主・配送日を変更できない（`orders_invoice_guard` トリガー）。変えるときは請求を取り消す
- 取り消し（`cancel_client_invoice()`）は請求を「取消」として残し、案件を未請求に戻す。番号は再利用しない。発行済みの請求の金額・期間は変更も削除もできない
- 同じ月に後から完了した案件は、追加の請求として発行できる
- 権限：`client_invoices` は参照とメモの更新だけを許可し、発行・取り消しは上の2関数（管理者のみ・自社のみ）経由。案件を直接請求にひも付けることもできない
- 既存の `delivery_orders.invoiced` は残し、`invoice_id` と常に一致させる（制約）
- 未請求金額 = 配送完了・未請求の料金（今月の締め前を含む）。荷主一覧・荷主詳細で同じ数字になり、各月の 売上 = 請求済み + 未請求（DB テストで確認）

### 権限（`20261027000003_rls.sql`）

| | 管理者 | ドライバー |
| --- | --- | --- |
| 自社の案件 | すべて閲覧・登録・更新・削除 | 自分の担当分のみ閲覧 |
| 案件の更新 | 直接更新可 | `driver_update_status()` 経由で 集荷完了・配送開始・配送完了・配送失敗 のみ |
| 経費・分析 | 閲覧・登録 | 不可（集計関数も管理者以外はエラー） |
| 請求 | 閲覧・発行・取り消し（関数経由） | 不可 |
| CSV 入出力 | 自社の案件の書き出し・取り込み | 不可 |
| 通知 | 管理者宛ての通知のみ | 自分宛ての通知のみ |
| 他社のデータ | 不可 | 不可 |

### 集計（`20261027000004_analytics.sql`）

すべての画面が同じ SQL 関数を使うため、画面ごとに数字が食い違わない。

- 売上 = 配送完了案件の配送料金（計上日 = 配送予定日）
- 配送原価 = 経費の合計
- 粗利益 = 売上 − 配送原価、粗利益率 = 粗利益 ÷ 売上 × 100（売上 0 円なら表示しない）
- 遅延 = 予定から15分を過ぎて完了、または予定を過ぎても未完了
- 前月比 = 今月1日〜今日 と 前月1日〜前月の同じ日 の比較

## 画面ごとの実装メモ（Phase 2）

### 配送案件（`/orders`）
- 検索条件はすべて URL に保持（再読み込み・共有で同じ結果）。サーバー側で Zod 検証し、不正な値は無視する
- 1ページ20件をサーバー側で取得（`LIMIT/OFFSET` と件数を別クエリ）。3,000件以上でも全件をブラウザに送らない
- 登録・編集フォームは画面とサーバーで同じ Zod スキーマ（`src/lib/validation/order.ts`）
- 削除できるのは集荷前とキャンセル済みのみ。集荷後はドライバー変更不可、完了・キャンセル後は担当と予定日時を変更不可（画面でも入力を止め、DB でも拒否）

### 配車ボード（`/dispatch`）
- 1日分の案件（キャンセル以外）を取得し、時間 × ドライバーで表示。重なる予定は段を分けて並べる（`src/lib/domain/board.ts`）
- ドラッグ（@dnd-kit/core）で担当変更。横方向の移動は15分単位で時刻変更、未割当の行へ戻すと配車解除
- **警告と保存禁止を分ける**
  - 警告：同じドライバーの時間が重なる → 確認ダイアログで「重複を承知で配車」を選べば保存（監査ログに記録）
  - 保存禁止：休職中・退職済みのドライバー、整備中の車両、集荷後の案件 → DB トリガーとサーバー側で拒否
- 画面に表示していた状態（ステータス・担当）を一緒に送り、DB と違えば保存しない（他の管理者・ドライバーとの同時操作対策）
- キーボード・スマホでは案件をクリック（タップ）して開くパネルから担当と時刻を変更できる

### ドライバー画面（`/driver`）
- データ取得はドライバー権限の RLS の中で行うため、他のドライバーの案件は URL を直接開いても表示されない
- ステータス更新は DB 関数 `driver_update_status()` のみ。取り消せない「配送完了」は確認を挟み、「配送失敗」は理由が必須
- 地図アプリへの案内は Google マップの公開 URL 形式（API キー不要）

### 通知（Phase 4 で追加した通知は後述）
- 割り当て・割り当て解除・時刻変更・再配達はドライバーへ、ドライバーの完了・失敗は管理者へ、DB トリガーで作成（`20261027000007_dispatch_notifications.sql`）
- 画面は通知・案件の変更を Realtime で受けて再取得する。担当を外れたドライバーにも「解除」の通知が届くので、その画面から案件が消える

## 画面ごとの実装メモ（Phase 3）

### ドライバー・車両・荷主（`/drivers` `/vehicles` `/clients`）
- 一覧の検索条件は URL に保持（`ListFilters`）。今月の実績は `analytics_by_driver` / `analytics_by_client` をそのまま結合するため、売上分析と必ず同じ数字になる
- 詳細の月別グラフは `analytics_order_series(期間, 'month', 荷主, ドライバー)`（`20261027000008_analytics_filters.sql`）。最後の棒（今月）は一覧の数字と一致する（DB テストで確認）
- 担当車両の変更（`assignVehicle`）：車両側・ドライバー側の今の担当を今日で終えてから新しい担当を作る。履歴は `vehicle_assignments` に残る
- 削除は実績がないときだけ。実績があるドライバーは「退職」、車両は「廃車」にする（売上・経費の履歴を残すため）
- 車検・保険は満了まで30日以内で注意、過ぎたら警告（`DEADLINE_WARNING_DAYS`、ダッシュボードと共通）
- ドライバー詳細：本日の担当案件（集荷予定順）・今月の実績・月別売上・配送履歴（前日まで）
- 荷主詳細：今月の売上と件数・未請求金額・月別売上・請求・取引履歴（月ごとの 配送完了／売上／請求番号／未請求、「請求済みにする」「取り消す」）。荷主一覧にも未請求を表示し、締め済みの月の未請求は強調する
- 案件詳細：請求済みなら請求番号を表示し、編集フォームで荷主・料金を変更できないようにする（サーバー処理と DB でも拒否）

### 売上・分析（`/analytics` `/analytics/expenses`）
- 期間：今月・先月・直近3か月・直近6か月・指定期間。サーバーで検証し、未来日は今日まで・最長2年。集計単位は45日以内なら日別、120日以内なら週別、それ以上は月別
- 比較：今月 → 前月の同じ日まで、先月 → 前々月、直近3・6か月 → その前の3・6か月、指定期間 → 直前の同じ日数
- 前の期間が0のときは増減率を出さない（0除算しない）。率の指標（粗利益率・遅延率）は「pt」の差で表示
- グラフの色は検証済みの順番（売上 ブルー / 経費 オレンジ / 粗利益 アクア）。1つの軸だけを使い、凡例と「表で見る」を付ける
- 荷主別・ドライバー別の売上ランキングに順位を表示（同額は同順位、売上0円は順位なし）
- 経費は未来日・3年より前を登録できない。登録・編集・削除は監査ログに記録し、分析とダッシュボードにすぐ反映する

## 画面ごとの実装メモ（Phase 4）

### 地図（`/dispatch?view=map`・ダッシュボード・ドライバーの「本日の配送」）
- Leaflet をブラウザでだけ読み込む（`import("leaflet")`）。地図を開いた画面だけが読み込むので、他の画面は重くならない
- マーカーの色と形：配送予定＝青、配送中＝オレンジ、配送完了＝緑、配送遅延＝赤、配送失敗＝灰。色だけに頼らず、ピンの中の記号と凡例の件数でも区別する（`src/lib/domain/map.ts`）
- 遅延は分析と同じ判定（予定 + 15 分）。遅れて完了した案件は緑のまま、吹き出しに「遅れて完了」と出す
- 吹き出しの文字はすべて `textContent` で入れる（住所や配送先名に HTML が含まれても実行されない）
- 位置はデモ用の近似座標（`approximateLocation()`）。「GPS による現在地ではない」ことを地図の下に必ず表示する
- タイルの URL は `NEXT_PUBLIC_MAP_TILE_URL` で差し替えられる（`src/lib/map-config.ts`）

### CSV 入出力（`/orders`）
- 書き出し（`/api/orders/export`）：一覧と同じ検索条件で、配送予定の古い順に最大 20,000 件。UTF-8（BOM 付き）・改行 CRLF なので Excel でそのまま開ける。`= + - @` などで始まる文字列には `'` を付けて、表計算ソフトで数式として実行されないようにする。書き出したことは操作履歴（`audit_logs`）に残す
- 取り込み：新しい案件の登録だけ（既存の案件は更新しない）。1回 500 行・512KB まで
  1. 文字コードを判定：BOM → UTF-8 → Shift_JIS（Windows-31J）。Excel の「CSV（コンマ区切り）」「CSV UTF-8」「Unicode テキスト」のどれでも読める（`src/lib/csv/csv.ts`）
  2. 列名で読み取る（ひな形の列名でも、書き出した CSV の列名でもよい）。全角英数字・空白の揺れはそろえる
  3. 自社のマスタと照合して確認画面を出す。**エラー**（荷主・ドライバーが見つからない、休職中・整備中、過去の日付、必須項目）があると登録できない。**注意**（同じドライバーの時間の重なり、同じ内容の案件が既にある、予定時刻を過ぎている）は確認のチェックを入れれば登録できる
  4. 登録の直前にもう一度すべて検証し、1つのトランザクションで全件を登録する（途中で1件でも失敗したら0件）。確認したファイルと違うファイル、確認後に注意が増えた場合は登録しない。同じ会社の取り込みは1つずつ行う（二重送信対策）
  5. 案件番号の採番・配車済への変更・ドライバーへの通知は、手入力の登録と同じ DB トリガーで行う

### 通知（`20261027000011_notifications.sql`）
- 追加した通知：遅延（管理者へ）、配車済みの案件のキャンセル・削除（担当ドライバーへ）、配送メモ（ドライバー → 管理者、管理者 → 担当ドライバー）
- 遅延は「時間が過ぎた」ことで起きるため、管理者の画面が開いている間、1分ごとに `refresh_late_alerts()` を呼ぶ（管理者のみ・自社のみ・1案件につき1回）
- 新しい通知が届いたら（Realtime または定期更新で一覧が変わったら）トーストでも知らせる。開いた通知はその1件だけ既読にする
- 通知は `order_id` で案件とひも付ける（案件が削除されても通知は残る）

### 同時操作と通信の切断
- 案件の編集は、編集を開いたときの「更新の印」（`updated_at` をマイクロ秒まで）を一緒に送る。その後にドライバーや他の管理者が更新していたら上書きせず、最新の内容を読み込むよう案内する
- 配車ボード・ステータス変更は、画面に表示していた状態を一緒に送り、DB と違えば保存しない（Phase 2 から）
- 通信が切れたら、画面上部に「表示は○時○分時点の内容」と出し、ドライバーのステータス操作ボタンを止める（送れなかった操作が完了したように見えないように）。通信が戻ると自動で再取得する
- ヘッダーに更新方法（リアルタイム／30秒ごと）と最後に取得した時刻を表示する

## 画面ごとの実装メモ（Phase 5）

### 表・関数の権限の締め直し（`20261027000012_harden_privileges.sql`）
- Supabase は public スキーマの表・関数・シーケンスに、既定で anon・authenticated へすべての権限を与える。RLS が守るのは行だけなので、TRUNCATE（RLS が効かない）や、RLS の条件に合う行の想定外の列の更新ができてしまう。いったんすべて取り消し、画面の操作に必要なものだけを許可し直した（今後作る表・関数も既定では許可しない）
- 表ごとの許可：会社は参照と名前の変更だけ、プロフィールは参照だけ（権限・所属会社は変えられない）、ステータス履歴は参照だけ（変更は DB 関数のトリガーが記録）、メモ・操作履歴は参照と追加だけ、通知は参照と既読にすることだけ、請求は参照とメモの更新だけ
- anon（未ログイン）には何も許可しない。実行できる関数は画面から使う14個だけで、期限切れデモの削除（`demo_cleanup()`）はサーバー（Cron）専用
- メモと操作履歴は、作成者・作成者名・日時を DB 側でログインユーザーと現在時刻に置き換える（なりすまし・日時の改ざんを防ぐ）
- 許可の一覧は DB テストで固定している（`tests/db/privileges.test.ts`）。許可を増やすときはテストも直す

### セキュリティヘッダー（`src/proxy.ts`・`next.config.ts`）
- リクエストごとに nonce を作り、Content Security Policy を設定する（`script-src 'self' 'nonce-…' 'strict-dynamic'`）。Next.js が自分のスクリプトに nonce を付ける。地図タイル・Supabase 以外への接続と、他サイトへの埋め込み（`frame-ancestors 'none'`）を禁止
- `X-Content-Type-Options`・`X-Frame-Options`・`Referrer-Policy`・`Permissions-Policy` を付け、`X-Powered-By` を出さない
- 未ログインで API を呼ぶと 401（JSON）、ドライバーが管理者用の API を呼ぶと 403 を返す（ログイン画面へのリダイレクトはしない）

### デモの数の上限
- 1社あたり約 12MB のため、同時に存在できるデモの数を `DEMO_MAX_ACTIVE`（既定 30）で制限する。上限に達したら期限切れのデモを削除してから数え直し、それでも空きがなければ匿名ログインの前に断る（「しばらくしてから」と案内）

### 設定（`/settings`）
- 会社名の変更（サイドバー・ヘッダーにすぐ反映）、営業所の追加・編集・削除。所属しているドライバー（退職者を含む）がいる営業所は削除できない
- 操作履歴：20件ずつ、種類（案件・マスタ・お金・設定）で絞り込める。案件やマスタへのリンクを付け、削除済みならリンクしない。ドライバーの割り当ては名前で表示する
- デモ環境では、自動で削除される日時と「デモデータを初期化」（現在の時刻に合わせて作り直し、期限を24時間延ばす）を表示する

### エラー処理
- Server Action の呼び出しはすべて `safeAction()` で包む。通信できなかったときは「接続を確認して…」とトーストで知らせ、入力内容を残す（`src/lib/client/safe-action.ts`）
- 画面の表示に失敗したら、管理者・ドライバー・全体それぞれのエラー画面（`error.tsx`・`global-error.tsx`）を出す。「再試行」でデータを取り直し、通信が戻ったときは自動で再試行する。問い合わせ用の番号（digest）を表示する
- 存在しない ID・権限のない ID は「見つかりません」を表示する

### 性能（`scripts/dev/perf.ts`）
- 会社を19社（案件 118,714件）に増やし、各画面のデータ取得を実際の権限（RLS）で計測。すべて 2〜50 ms（案件一覧 44 ms、1社の全案件の CSV 書き出し 122 ms）。案件は `(company_id, delivery_at)` などの索引で絞り込まれる

### 売上・分析の比較
- 比較する期間の途中から記録が始まっている場合（例：記録が6か月分しかないときの「直近6か月」）は増減率を出さず、記録の開始日を表示する。記録のない日を 0 として比べると極端な値になるため

### デモデータの配車
- 全員の予定が埋まっているときは、次に空くドライバーの空き時間へ後ろ倒しする（荷主と時間を調整した想定）。予定が重なるのは、その日のうちに収まらない場合だけ（単体テストで 0 件を確認）
- 夜など、本日の配送がすべて終わったあとは、ダッシュボードと配車ボードに「明日の予定」への案内を出す

### E2E テスト（`tests/e2e`・`playwright.config.ts`）
- PC（1280px）とスマートフォン（390px）で実行する。テストごとに「体験」ボタンから専用のデモ会社を作り、終わったら削除する（DB の整合性チェックの対象に残さない）
- 画面で JavaScript のエラー（CSP の違反を含む）が出たら失敗にする。地図タイルは灰色の画像に差し替え、外部のサーバーに依存しない
- CI ではビルドしたアプリを `next start` で起動して実行し、失敗したときはトレースとスクリーンショットを保存する
- `E2E_BASE_URL` を指定すると、アプリを起動せずにその URL（公開環境）に対して実行する（`.github/workflows/production-e2e.yml`）

### 公開環境のセットアップ（`.github/workflows/production-db.yml`）
- 開発環境から Supabase に接続できない前提で、DB の構築は GitHub Actions から手動で実行する。接続情報・Secret key・ログイン用パスワードは GitHub の Secrets にだけ置き、ログにもチャットにも出さない
- 登録値の確認（`scripts/deploy/`。直接接続や Transaction pooler、既定パスワードを理由付きで弾く）→ `supabase db push` → 見本の会社とログイン用アカウントの作成 → 整合性チェック。何度実行しても同じ状態になる
- 見本の会社のパスワードは README に載っている既定値を公開環境では使わない（`SUPABASE_SERVICE_ROLE_KEY` があるときは未設定ならエラー）。新しい Secret key（`sb_secret_…`）は JWT ではないので `apikey` ヘッダーだけで送る

## デモ環境

- 体験ボタン → Supabase の匿名ログイン → 訪問者専用の会社を生成（`src/lib/demo/sandbox.ts`）
- データは「今」を基準に生成する。過去6か月の実績、本日の進行中の配送、今後1週間の予定
- 24時間後に自動削除。デモ会社に限り管理者⇔ドライバーを切り替え可能（`demo_switch_role()`）

## デモデータ

架空の「株式会社ミナトエクスプレス」（東京・神奈川で企業間配送）。ドライバー15名（正社員10・業務委託5）、車両18台、荷主12社、直近3か月で約3,000件。

平日と休日の差、月末の増加、7月・12月の繁忙期、お盆の減少、荷主ごとの単価と依頼量の偏り、ドライバーごとの件数・遅延率の違い、件数に比例する燃料費・高速代・外注費を再現している。請求は締め済みの月を翌月5日に発行した状態で作り、直近の締め月は3社を未請求のまま残す（「請求済みにする」を試せるように）。整合性は `npm run db:verify` と DB テストで確認する。直近7日分の操作履歴（案件の登録・配車・請求）も、画面から操作したときと同じ形で作る。
